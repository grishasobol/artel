# One prompt for many models and harnesses: what to share, what to specialise, who tunes it

## Conclusion
artel should keep one canonical text per prompt module and per skill, written in the register that all three
frontier vendors now converge on: calm, outcome-first, reasons given, few absolutes reserved for real
invariants. It should not keep per-harness or per-model copies of whole prompts in the repository. What
genuinely differs between models is a short list of behavioural defaults (delegation, asking versus acting in
unattended runs, progress updates, verbosity, reasoning echo, sampling and message structure for open models).
That list belongs in a small curated `models/` layer of the prompt library, and the super agent applies it when it
compiles an identity for an agent whose harness and model it already knows. The super agent may tune a compiled
identity for its model, but only as a measured, reversible delta; it must not author library modules or skills on
its own, because the best current evidence says self-written skills make agents worse on average while curated
ones make them better. Most real cross-harness failures are mechanical (paths, frontmatter, parser strictness,
size caps), so the cheapest and most valuable addition is a deterministic linter, not more prompt text.

## 1. How artel uses prompts today
| layer | who reads it | written for | specialised by |
|---|---|---|---|
| `charter.md` | every agent, every run | all harnesses and models | nobody (invariants) |
| skills `super`, `artel-create` | whichever harness the user or timer runs | all four harnesses, any model | nobody; one file symlinked into every skill directory |
| prompt library `templates/prompts/` | only the super agent, as raw material | the super agent | `harness/*` modules hold harness mechanics (flags, quotas, traps), not model style |
| identity `agents/agent-<name>.md` | one worker agent | one agent on one harness and model | the super agent compiles it (`artel/team-design`), with a "Harness and model" line |
| run prompt | the worker | generated by `artel run` | nobody |

So artel is already a compile step: the expensive model distils a library into a per-agent prompt and knows the
target harness and model while doing so. The question is therefore not whether to specialise, but what the
compiler should know about the target, where that knowledge lives, and how changes are controlled.

Audit of the current texts (2026-10-27, `grep` over `templates/`, `charter.md`, `.agents/`, `docs/install.md`):
no ALL-CAPS emphasis (`MUST`, `NEVER`, `IMPORTANT`, `CRITICAL`), no "show your reasoning" instructions, skill
descriptions of 573 and 509 characters (limit 1,024), `super` SKILL.md 226 lines (limit 500), no BOM, root
`AGENTS.md` 6.9 KB and the project `AGENTS.md` 2.5 KB (Codex cap 32 KiB, agy 24,000 bytes per file). The only
Claude-specific frontmatter key is `argument-hint` in `super`, which other harnesses ignore. The charter names
harness tools (`Agent tool`, `spawn_agent`, `invoke_subagent`) side by side, which is the mapping-table style
other multi-harness projects use. The house rule "results and verifiable checks, not step lists" already matches
the newest vendor guidance.

## 2. What the vendors say
### Where they agree
- **Calm wording, few absolutes.** Claude Code's best-practices page lists adding IMPORTANT or ALL CAPS as an
  anti-pattern: current models follow a plain line, and emphasis "mostly makes Claude over-apply the rule"
  (checked). Anthropic's prompting guide says prompts written against under-triggering now over-trigger and tells
  you to soften "CRITICAL: You MUST". OpenAI's GPT-5.5 guide reserves ALWAYS/NEVER/MUST for true invariants
  such as safety rules and required fields, and wants decision rules for judgment calls (checked). Google's
  prompt-design page asks for direct goals without persuasive language and warns that broad "do not" rules are
  over-applied.
- **Outcomes over procedures.** OpenAI: legacy prompts over-specify process because earlier models needed it;
  start migration from a fresh minimal baseline and let the model choose the path unless the path matters
  (checked). Anthropic's Fable 5 page: skills developed for prior models are often too prescriptive for Fable 5
  and can degrade output; steer with a brief instruction instead of enumerating behaviours (checked).
- **Give the reason.** Anthropic (general guide and Fable 5) and OpenAI both say intent behind a rule lets the model
  generalise; Google says to define ambiguous terms.
- **Short instruction files.** Claude Code: CLAUDE.md under 200 lines, longer files reduce adherence; rules that
  cannot bend belong in hooks. Codex: "keep rules short and specific", 32 KiB cap. agy: 24,000 bytes per rule file
  and a 20,000-token budget for always-on rules.
- **Re-test on every model change.** Anthropic says to treat model-named advice as measured on that model and to
  re-check it with your own evals; OpenAI says to switch the model first, run evals, then add the smallest fix per
  measured regression.

### Where they conflict
| topic | Claude | GPT / Codex | Gemini / agy | consequence for one shared text |
|---|---|---|---|---|
| sub-agents | Opus 4.6 and Opus 5 over-spawn; Fable 5 delegates readily | GPT-6 Astra "may delegate less often than desired" (checked) | Antigravity docs tell the main agent to spawn background sub-agents for sweeps | the delegation rule must be explicit in every identity; the default pushes in opposite directions |
| progress updates | Fable 5.1 and Sonnet 5.5 write fewer; ask explicitly | GPT-5.5 wants a 1-2 sentence preamble; Codex guide says status prompting on pre-5.3 models caused abrupt stops | direct and terse by default | specify per model or leave to the harness |
| reasoning in the answer | asking Fable 5 or Sonnet 5.5 to echo its reasoning can trigger a `reasoning_extraction` refusal (checked) | harmless; ask for validation by tests instead | thinks internally; templates still mention step-by-step | never put "explain your thinking" in shared text |
| ask versus act | Fable 5 may stop to ask in unattended runs; tell it it runs autonomously | GPT-6: treat "can you" as authorisation, bias to action | Gemini CLI core prompt is the most proactive; project files cannot override it | unattended-run framing is required for Claude, partly redundant for others |
| process steps | low-freedom exact steps for fragile operations (skill guide) | drop step-by-step guidance | Plan/Execute/Validate template, step bodies in codelab | steps only where the path itself is the requirement |
| structure | XML tags recommended | XML-style sections helped (GPT-5) | XML or Markdown, but never both in one prompt | pick Markdown, be consistent |
| examples | 3-5 in tags | not emphasised | "always include few-shot examples" | examples help open models more than frontier ones (section 4) |
| sampling | n/a in subscriptions | n/a | Gemini 3: temperature 1.0; Gemini 4 ignores it | opencode defaults temperature 0 for most models, while Kimi and Qwen recommend 1.0 |

Anthropic's own skill-authoring page still shows ALWAYS/MUST templates and suggests stronger wording when a rule
is missed. It predates the over-triggering guidance and conflicts with the newer pages; artel should follow the
newer ones.

Open-weight vendors (Zhipu GLM, Moonshot Kimi, Qwen, DeepSeek) publish sampling and tool-protocol requirements
(temperature, passing `reasoning_content` back, tool schema), not prompt-style guidance. Style advice for them can
come only from measurement.

## 3. Mechanical portability: the layer that actually breaks
| item | Claude Code | Codex | agy | opencode |
|---|---|---|---|---|
| project skill directory | `.claude/skills` (`.agents/skills` not documented) | `.agents/skills` and parents; follows symlinks | `.agents/skills` | `.opencode/skills`, `.claude/skills`, `.agents/skills` |
| instruction file | CLAUDE.md; AGENTS.md only if no CLAUDE.md, or via `@AGENTS.md` | AGENTS.md (override files, 32 KiB total) | AGENTS.md and GEMINI.md, 24,000 bytes each | AGENTS.md, falls back to CLAUDE.md; ignores `@` imports |
| frontmatter read | spec fields plus many extensions; unknown keys ignored (but the Skills API rejects them) | `name`, `description`; extras in `agents/openai.yaml` | `description` required, `name` optional | spec fields; unknown keys ignored |
| listing budget | description plus `when_to_use` cut at 1,536 chars; listing about 1% of context | skill list about 2% of context, descriptions shortened first | not published | not published |

Practitioner reports of "works in Claude, not in X" are mostly of this kind: Codex skipped a skill whose
single-quoted description contained an apostrophe while Claude loaded it; a UTF-8 BOM made Codex skip files;
`skill.md` in lower case is ignored on Linux; hooks and sub-agent types that exist in one harness only. A
deterministic check catches all of these; a model cannot.

Triggering is the least reliable layer everywhere. Vercel's eval (2026-01-27, checked): a skill alone did not
improve on the 53% baseline because it was never invoked in 56% of cases; an explicit instruction raised the pass
rate to 79%, and a compact docs index placed in AGENTS.md reached 100%. Their "You MUST invoke the skill" wording
made the agent anchor on the docs and miss project context. artel is largely immune: its skills are invoked
explicitly (`/super`, `/artel-create`), and worker know-how reaches the worker as its identity file, not as an
auto-triggered skill. That design should stay.

## 4. Evidence on transferring one prompt across models
- **Format sensitivity is large and model-specific.** FormatSpread (Sclar et al., ICLR 2024): format-only changes
  moved accuracy by up to 76 points on LLaMA-2-13B and 56 on GPT-3.5, median about 7; whether one format beats
  another on one model predicts the same ordering on another model only slightly better than chance (below 0.62).
  Mind Your Format (2024, 21 models) and He et al. (2024, GPT-3.5 versus GPT-4) agree; GPT-4 was the most robust.
  These are older, smaller models and classification-like tasks, so magnitudes overstate the effect on 2026
  frontier models.
- **Transfer losses are asymmetric.** PromptBridge (Wang et al., December 2025; abstract checked, numbers from the
  HTML body): on HumanEval, GPT-5's best prompt scores 99.4 on GPT-5 but 68.7 on Llama-3.1-70B, against 79.5 for
  Llama's own optimised prompt, while Llama's prompt on GPT-5 loses only 2.4 points. Prompts tuned on a strong
  model hurt weak models most. Their mapping step recovers +27% on SWE-Bench and +39% on Terminal-Bench over
  direct transfer.
- **Counter-evidence.** GEPA (ICLR 2026) prompts optimised on Qwen3-8B and run unchanged on GPT-4.1 Mini gained
  9 points, more than optimisers run directly on GPT-4.1 Mini. Transfer is not uniformly bad; it depends on the
  optimiser and task.
- **Scaffolding ages.** Aging of Prompt Engineering Techniques (Rudyk, Oertel, Hebig, August 2026, checked):
  newer GPT models show diminishing or negative gains from structured prompting such as chain of thought, while
  the newer Qwen still benefits from few-shot and contrastive CoT; the authors conclude strategies must be adapted
  per family and generation.
- **Same vendor, new version, still breaks.** Item-level regressions in API migrations (Xu and Wu, August 2026):
  moving from GPT-5.4 to 5.6 with up to +7.3 points in aggregate still made up to 8.3% of items regress reliably.
- **Instruction density decays differently per model.** IFScale (2025): with hundreds of simultaneous
  instructions the best model reached about 68%, and decay curves differed by model (threshold, linear,
  exponential), with a bias toward earlier instructions.
- **No controlled study** compares the same SKILL.md or AGENTS.md across Claude, GPT and Gemini, and none covers
  GLM or Kimi. The one paper on AGENTS.md efficiency tested only a Codex model.

Reading for artel: the loss from sharing one text is real but concentrated in two places, weaker open models and
heavily scaffolded prompts. A neutral, outcome-first text is the cheapest form to share, because the scaffolding
that does not transfer is exactly what it omits; the open-model gap is better closed by a short overlay with more
explicit structure and examples than by a separate prompt.

## 5. Evidence on agents tuning their own prompts and skills
- **Self-written skills hurt; curated skills help.** SkillsBench (Li et al., arXiv 2602.12670, v4 June 2026,
  checked): curated skills raise the average pass rate from 33.9% to 50.5% over 87 tasks and 18 model-harness
  configurations. Skills the agent wrote for itself scored below no skills at all: Claude Code with Opus 4.7
  -8.1 points, Codex with GPT-5.5 -11.3, Gemini CLI with Gemini 3.1 Pro -11.5 (section 5.1.1, checked). The
  authors' audit names packs the solver never found, authoring that displaced real work, and confidently wrong
  content. The same paper: one skill +18.0, two or three +19.0, four or more +10.1; compact +19.0, standard +21.5,
  detailed +14.5, comprehensive +0.7.
- **Self-improvement works with a trustworthy signal.** GEPA uses separate feedback, selection and test sets and
  ends with prompts up to 9 times shorter than MIPROv2's. ACE (ICLR 2026) gains +17 on AppWorld by keeping context
  as itemised bullets that a curator updates with small deltas merged by plain code. Without reliable labels its
  online gain on one finance task turned negative (-3.4).
- **Monolithic rewriting collapses.** ACE documents a context of 18,282 tokens rewritten into 122, with accuracy
  falling from 66.7 to 57.1, below the 63.7 no-adaptation baseline ("context collapse"); optimisers also drift
  toward short generic text ("brevity bias").
- **Evolution erodes safety properties.** "Your Agent May Misevolve" (2025) and its follow-up report safety and
  trustworthiness falling as memory accumulates, even with ground-truth feedback.
- **Guards that worked.** The Darwin Gödel Machine (SWE-bench 20% to 50%) ran in a sandbox with human oversight
  and kept an archive of variants; news reports say hiding the checker from the agent reduced reward hacking.
  Voyager and SkillWeaver admit a skill only after it runs successfully. OpenAI's migration advice is the same
  pattern in miniature: eval first, smallest fix per measured regression, never a whole-stack rewrite.
- **Vendors expect some model-side self-maintenance.** The Fable 5 page notes the model does a good job updating
  skills from what it learns on the current task. That is about a skill in the agent's own working loop, not about
  rewriting shared infrastructure without checks.

Reading for artel: a super agent that freely rewrites the library, the charter or skills would sit in the
SkillsBench "self-generated" arm and risk context collapse. A super agent that changes one identity at a time,
by a small delta, with a before-and-after metric and rollback, sits in the GEPA and ACE arm. artel's
`artel/team-design` already describes the second ("minimal, targeted edit, one change at a time", snapshot,
journal entry, check the next runs, restore from `history/`); what is missing is a metric (phases 6 and 9 of
`todo.md`) and a path for lessons to reach the library through curation.

## 6. What multi-harness projects do
- **One tree, mapping tables, per-harness bootstrap.** obra/superpowers keeps a single `skills/` tree written in
  terms of actions, with a per-harness tool map (Claude `Task`, Codex `spawn_agent`, opencode `task`). Its release
  notes (checked) are the best public log of what breaks: v5.0.7 (2026-03-31) moved the opencode bootstrap from a
  system message to the first user message because Qwen and other models break on multiple system messages;
  v6.1.0 (2026-06-30) removed a Codex-specific hook because Codex "reliably triggers skills on its own" and the
  hook made things worse; v6.4.2 (2026-09-25) rewrote the planning skill because some frontier models, including
  Opus 5.5, became overzealous and started implementing during planning. Two of three fixes changed the shared
  text or removed a harness special case; one was a harness mechanic.
- **Render per host and per model.** garrytan/gstack renders each skill from a template per host (frontmatter
  allowlist, path and tool-name rewrites, suppressed sections) and adds per-model overlays for Codex-GPT and
  Gemini. Only Claude Code has "Full" support; the other hosts are "Experimental". The render pipeline is real
  engineering and still leaves most hosts second-class.
- **Sync tools copy bytes.** Ruler, the vercel `skills` CLI, Skillshare and openskills copy or symlink identical
  skills into each harness directory; none rewrites skill bodies per agent. Only rulesync allows per-target
  frontmatter overrides. `.agents/skills` is the neutral directory read by Codex, agy, opencode and about twenty
  other tools; Claude Code is the main holdout and is reached by symlink, as artel does.
- **Vendor collections ship one variant.** anthropics/skills and openai/skills contain no per-harness variants.

## 7. Options for artel
| option | what it means | for | against |
|---|---|---|---|
| A. one text everywhere, as now | library and skills neutral; identities compiled without model knowledge beyond mechanics | simplest; matches vendor convergence; skills are invoked explicitly | known behavioural differences (delegation, unattended-run framing, open-model structure) are left to chance or rediscovered in every project |
| B. per-harness or per-model copies in the repository | `harness/claude/worker.md`, `models/glm/leader.md` and so on | each text can be tuned | modules times harnesses times models; the copies age with every model release (section 4); no eval to tell whether a copy is better; gstack shows the cost and still has one first-class host |
| C. super agent tunes freely per model | super agent rewrites library modules or writes model-specific skills on its own | adapts to the actual project and models | negative evidence for unsupervised self-authored skills (-8 to -11.5 points); context collapse; drift of invariants; lessons stay trapped in one project |
| **D. neutral core + curated model notes + measured compile-time adaptation (recommended)** | one text per module; a short `models/` layer of behavioural deltas maintained in the repository; the super agent applies them while compiling identities, then tunes by measured deltas; lessons flow back as `artel-issue` entries and are curated | reuses the compile step artel already has; keeps the evidence-backed split between curated content and measured adaptation; small maintenance surface | needs a metric to be honest (phases 6 and 9); the model notes must be pruned on every model generation |

## 8. Recommendation in detail
1. **Keep one canonical text per library module and per skill.** Write it outcome-first, with reasons, Markdown
   only, no emphasis, absolutes only for charter-level invariants, no requests to show reasoning, an explicit
   delegation rule and an explicit length and format expectation. Name harness tools in a mapping line where
   they differ, as the charter already does. Keep worker know-how out of auto-triggered skills.
2. **Separate model from harness.** agy runs Gemini and also Claude and GPT-OSS models; opencode runs GLM, Kimi,
   Qwen and DeepSeek. `harness/*` stays about mechanics. Add a `models/` group with one short module per family
   (`models/claude`, `models/gpt`, `models/gemini`, `models/open-weights`), 10 to 25 lines each, holding only the
   behavioural deltas with their source and the model versions they were observed on: for example "Claude runs
   unattended: say so, and say when to stop and ask", "GPT-6 Astra under-delegates: state when to use workers",
   "open-weight models: more explicit structure, one worked example, a single system message, temperature as the
   vendor recommends". Each note carries a `checked:` date and model list so it can be pruned when a new
   generation makes it obsolete.
3. **Let the super agent apply the notes at compile time.** `artel/team-design` gains one source rule: the
   `models/<family>` module of the agent's model is a compilation source like `harness/<name>`, distilled into the
   identity, and recorded in `sources:` so `artel prompts status` reports staleness. A model or harness change for
   an agent counts as a prompt change: recompile from the library rather than carry the old identity over.
4. **Allow per-model tuning of identities only as measured deltas.** The existing tuning procedure (snapshot, one
   targeted edit, journal entry, check the next runs, restore) becomes an experiment once phase 6 (`runs.jsonl`,
   `artel stats`) and phase 9 (`artel experiment`) exist: hypothesis, the metric it should move, a run budget, and
   automatic rollback. The super agent does not edit `artel/`, the charter or library modules (already forbidden),
   and should not write new skills for workers; a pattern worth keeping becomes a script (phase 9
   crystallisation) or a project module in `agents/prompts/`, which is reviewed like any other identity source.
5. **Close the loop through curation.** When a super agent finds a model-specific fix that held for several runs,
   it records it as an `artel-issue` journal entry with the evidence. The maintainer (or a lead session in this
   repository) promotes it into `models/*` after checking it, and deletes notes that newer models no longer need.
   This keeps the library in the "curated" arm of the SkillsBench result.
6. **Add a deterministic portability check.** `artel lint` (or a step of the planned `tests/smoke.sh`) over
   `templates/skills`, `.agents/skills`, the generated project skills and instruction files: `SKILL.md` name and
   case, `name` equal to the directory, description at most 1,024 characters with the use case in the first
   sentence, body under 500 lines, YAML that loads under a strict parser, no BOM, no Claude-only keys except an
   allowlist (`argument-hint` today), instruction files under the smallest cap (Claude 200 lines is a
   recommendation; Codex 32 KiB and agy 24,000 bytes are hard), and no ALL-CAPS emphasis or reasoning-echo
   phrases. This catches the failure class practitioners actually hit.
7. **Measure before believing any of this for open models.** No source covers GLM or Kimi prompt style. The first
   project that runs an opencode worker should record, per model, the share of runs that end `advanced` versus
   `noop` or `failed` (phase 6 outcome field) before and after applying the `models/open-weights` note.

These recommendations are phase 10 of `todo.md` (steps 10-01 to 10-06).

## 9. What could not be verified
- Whether Claude Code reads `.agents/skills` (documentation is silent; secondary sources say no). artel's
  symlinks into `.claude/skills` make this moot.
- How Codex and agy treat unknown frontmatter keys; whether agy honours `allowed-tools`.
- PromptBridge and ACE numbers were read from the HTML versions, not the PDFs; SkillsBench appendices with the
  per-size breakdown for self-generated skills were not reached. The skill-count and skill-size numbers in
  section 5 refer to curated skills.
- Mind Your Format, IFScale, Dynamic Cheatsheet, Voyager, SkillWeaver and the Darwin Gödel Machine reward-hacking
  details come from abstracts or secondary summaries only.
- Several 2026 arXiv papers (Aging of Prompt Engineering, Item-Level Regressions, SkillEvolver, SkillAxe) are
  recent and probably not yet peer-reviewed.
- Page dates: most Anthropic, OpenAI and Antigravity documentation pages show no date; they were read on
  2026-10-27.
